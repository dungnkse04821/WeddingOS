# M8.4 NFR Benchmark Evidence

Date: 2026-08-29

## Approved Targets

| NFR | Approved target | Fixture | Result |
| --- | --- | --- | --- |
| Android task/guest list | under 2 seconds | 500 tasks / 300 guests | PASS locally; task 26 ms and guest 19 ms median initial render over five widget-test repetitions. |
| Guest Web first useful invitation content | under 3 seconds | production build, synthetic invitation DTO, fixed Chrome 4G | PASS; 622 ms median over three cold-cache runs. |
| Excel import preview | under 5 seconds | 300 synthetic XLSX rows | PASS; 43 ms median over five parser repetitions. |

The target sources are `REQ-06-NFR`, `STORY-13-02`, and the performance gate in
`docs/planning/11-implementation-plan.md`. They specify no numeric Finance,
Edge, or Storage-latency target; those measurements are diagnostics only.

## Reproducible Harnesses

- `tests/performance/m8_4_db_benchmark.ps1` creates a disposable local fixture,
  uses `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` five times per delivered query,
  reports median/min/max and plan nodes, then removes all fixture rows.
- `organizer_app/test/m8_4_local_benchmark_test.dart` uses the delivered models,
  a lazy `ListView`, and the real XLSX parser. It is a local widget/render
  measurement, not a replacement for device profiling.
- `tests/performance/m8_4_guest_web_4g_benchmark.mjs` builds Guest Web into a
  temporary directory, serves that production bundle, and uses headless Chrome
  DevTools Protocol with a fixed 4G profile: 150 ms latency, 4 Mbps download,
  and 3 Mbps upload. It uses a synthetic non-PII invitation response so bundle
  loading/rendering is measured separately from the real Edge resolve path.
- `supabase/tests/m8_2a_edge_provider_smoke.ps1` is the existing real-provider
  fixture, extended to emit request timings for resolve, RSVP, and 101-object
  Wedding deletion.

No fixture contains real PII, credentials, tokens, signed URLs, or retained
provider objects.

## Database Results

Fixture: 500 tasks, 300 guests, 100 payments, 100 refunds, and 100 installments.
All times are local Postgres execution medians across five warm repetitions.

| Query | Median ms | Min-Max ms | Plan nodes |
| --- | ---: | ---: | --- |
| Task list ordered by `created_at` | 0.180 | 0.172-0.230 | Seq Scan, Sort |
| Guest list ordered by `name` | 0.190 | 0.179-0.224 | Seq Scan, Sort |
| Budget list ordered by `created_at` | 0.066 | 0.057-0.090 | Seq Scan, Sort |
| Installments ordered by `due_date` | 0.093 | 0.077-0.104 | Seq Scan, Sort |
| Payments ordered by `payment_date` | 0.087 | 0.085-0.096 | Seq Scan, Sort |
| Refunds ordered by `refund_date` | 0.096 | 0.080-0.104 | Seq Scan, Sort |
| Finance summary | 1.163 | 0.994-1.412 | Aggregate, Append, Hash Join, Nested Loop, Sort |
| Current membership lookup | 0.046 | 0.044-0.053 | Index Scan |
| Invitation credential hash lookup | 0.047 | 0.042-0.056 | Index Scan |

The sequential plans are expected for these small, Wedding-scoped MVP fixture
sets and are substantially below any approved UI target. No index was added.
The invitation credential hash unique index remains in place; this benchmark
does not show material evidence to remove it, so M8-P3-001 remains tracked debt.

## Guest Web and Edge Results

- Guest Web fixed-4G production-bundle first useful content: 623, 614, and
  622 ms; median 622 ms, target under 3,000 ms: PASS.
- Real local Edge/provider: invitation resolve 82 ms, RSVP 63 ms, and complete
  101-object Storage cleanup plus finalization 176 ms. The deletion fixture
  observed provider list pages of 100 and 1 entries, followed by a fresh empty
  list and Auth-user preservation.
- The Edge/Storage values have no separately approved latency threshold. They
  establish local timeout headroom only; delete remains deliberately retry-safe
  rather than optimized for a constant duration.

## Tuning Decision

No production index, query-shape, Flutter list, or Guest Web optimization was
made. Every approved local benchmark passed, and query plans did not reveal a
material inefficiency at the approved fixture sizes. There is therefore no
before/after production tuning comparison to report.

## Environment Limitations

- The Android target was exercised through reproducible Flutter widget tests,
  not a physical Android device or emulator. No ADB device/emulator is available
  in this local environment. M8.5/staging must repeat the same fixtures on the
  agreed Android reference device/network.
- The Guest Web measurement uses a controlled Chrome CDP 4G profile and a
  synthetic invitation DTO. Real resolve latency is separately proven locally;
  a deployed staging 4G run remains M8.5 release evidence.
- The checked-in ignored `guest_web/dist` directory is owned by the local Codex
  sandbox account and cannot be regenerated by the workspace identity. The
  harness builds the identical production bundle in a fresh temporary directory
  and deletes it afterward. This is a local artifact-permission issue, not a
  source, build, or product failure.
