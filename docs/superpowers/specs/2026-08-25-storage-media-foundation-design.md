# Storage & Media Foundation Design Specification
Date: 2026-08-25

## A. Milestone Identity & Traceability
- **Milestone Name/ID**: `M6 — Storage & Media Foundation`
- **Original Planned ID**: `M5 — Storage & Media Foundation`
- **Numbering History**: The practical milestone numbering has drifted because *Finance Core* (originally parallel stream `M2C`) was pulled forward and implemented as `M5`. The original `M5` is now implemented as `M6`.
- **Milestone Scope Integrity**: This milestone is kept strictly separate from the future `M7 — Wedding Lifecycle & Cleanup` milestone. Archiving and permanent deletion operations are explicitly out of scope.

## B. Source Requirements & ADR Traceability
- **`REQ-05-001`**: Render public wedding cover photo dynamically.
- **`REQ-06-NFR` / `XCT-NFR-006`**: Automatically optimize wedding photo sizes, enforce max upload limit of 5MB.
- **`ADR-006`**: Private Storage access model baseline. Eliminates persistent storage of raw XLSX source files.
- **`ERRATA-D-003`**: Media expiry configuration is a dynamic, server-side parameter on the Edge Function runtime, not an immutable API v1 contract.

## C. Private Bucket Contract
- **Bucket Name**: `wedding_media` (resolving the previously deferred bucket name convention in `ADR-006`/`DEC-B-003`).
- **Access Mode**: Strictly **PRIVATE**. Standard public download URLs are disabled. No direct anonymous public read access is allowed via the storage layer.

## D. Static Object Path Contract
- **Path Schema**: `weddings/{wedding_id}/cover.webp`
- **Single-slot Semantics**: Each wedding has exactly one cover image in MVP. The path is deterministic, resolving to a single file. Overwriting the path replaces the cover image directly, preventing orphaned files from accumulating.
- **No Galleries**: Galleries, multi-media folders, video uploads, and general media libraries are explicitly excluded from `M6`.

## E. Organizer Permission Matrix
For an `ACTIVE` wedding workspace:
- **OWNER**: 
  - `SELECT` (read cover): Allowed.
  - `INSERT` (upload initial cover): Allowed.
  - `UPDATE` (replace cover): Allowed.
- **COLLABORATOR**: 
  - `SELECT` (read cover): Allowed.
  - `INSERT` (upload initial cover): Allowed.
  - `UPDATE` (replace cover): Allowed.
- **Guest / Public**: 
  - Direct Storage access is **Denied** (no authenticated sessions can read/write directly). Reads are only permitted through signed URLs generated by the trusted resolve Edge flow.

For an `ARCHIVED` wedding workspace:
- **OWNER / COLLABORATOR**: Read access to cover remains available via regular authenticated reads. Write mutations (upload/replace) are blocked by database RLS triggers checking workspace status.
- **Guest / Public**: Guest resolve is blocked from generating new signed URL photo links for archived weddings.

*Note*: No standalone "delete cover image" operation/UI is required for `M6`. Deleting media is strictly handled via the future `M7` permanent deletion of the entire wedding workspace.

## F. Storage Policy Model
Policies are configured in PostgreSQL on the `storage.objects` table. The bucket ID constraint is strictly checked:
- **Insertion/Update Policy**:
  ```sql
  CREATE POLICY "Active members can mutate cover photo" ON storage.objects
  FOR ALL TO authenticated
  USING (
    bucket_id = 'wedding_media' AND
    (storage.foldername(name))[1] = 'weddings' AND
    security.is_active_wedding_member((storage.foldername(name))[2]::uuid)
  )
  WITH CHECK (
    bucket_id = 'wedding_media' AND
    (storage.foldername(name))[1] = 'weddings' AND
    (storage.foldername(name))[3] = 'cover.webp' AND
    security.is_active_wedding_member((storage.foldername(name))[2]::uuid)
  );
  ```
- **Cross-tenant Isolation**: Authenticated members can only read and modify files nested under their active `wedding_id` folder. Client-supplied `wedding_id` parameters are never trusted directly; they are always parsed server-side from the object name path.

## G. Provider Runtime Model
- **Client Runtime**: The Flutter organizer client uses the standard Supabase Storage SDK Client API wrapper (HTTPS calls) passing the user's Supabase Auth session JWT. The Supabase Storage API parses this session and maps the DML assertions directly to PostgreSQL table operations, where the database policies are evaluated.
- **Trusted Edge Runtime**: The invitation resolve Edge Function does not bypass RLS using SQL. It uses the Supabase Server Client initialized with the `service_role` key to call the trusted Storage API's `createSignedUrl()` endpoint, returning a short-lived link to the client.

## H. Image Format, Size & Client Optimization Rules
- **Approved MVP Source Formats**: `JPEG`, `PNG`, `WebP`.
- **SVG Restriction**: SVG uploads are blocked to prevent cross-site scripting (XSS) and XML Entity injection.
- **Flutter Client Optimization**:
  1. Pick a supported source format.
  2. Validate format header magic bytes (JPEG/PNG/WebP).
  3. Resize and compress on-device to WebP format.
  4. Enforce file size limit $\le$ 5MB before initiating upload.
  5. Reject with clear UX warning if compression fails or size limit is exceeded.
- **Backend Defense-in-Depth**: The `wedding_media` bucket is configured with standard Supabase limits: max file size `5MB` and permitted MIME types (`image/jpeg`, `image/png`, `image/webp`).

## I. Upload & Replace Semantics
- **Upsert Operation**: Because the cover path `weddings/{wedding_id}/cover.webp` is static, replacement uses the overwrite parameter (`upsert = true` in Supabase SDK).
- **Network Fail-Safe**: The client performs updates inline. In the event of a network failure or compression error, the local update halts before calling the storage API, preserving the existing cover image on the server.

## J. Signed URL Generation
- **Issuer**: Generated on Deno Edge runtime inside the `D-INV-001` resolve handler using the standard client.
- **Exclusion**: The raw Storage object path (e.g. `/storage/v1/object/private/wedding_media/...`) is never returned to the public guest client. Only the signed tokenized URL is exposed.

## K. 30-Minute Configurable TTL
- **Default TTL**: `1800` seconds (30 minutes), as outlined in `07-class-d-public-guest-api-design.md` line 100.
- **Design Rule**: The 30-minute expiration is a dynamic runtime parameter. The client application must not bake business assumptions or hardcode caching logic around a fixed duration.

## L. D-INV-001 DTO Amendment
- **New Field**: `cover_photo_signed_url` (nullable string).
- **Behavior**:
  - If a cover exists and the invitation is currently eligible for guest resolve (active invitation, active wedding): returns the dynamic 30-minute signed URL.
  - If no cover has been uploaded: returns `null`.
  - If the wedding is `ARCHIVED` or invitation status is invalid: the resolve endpoint returns a `404 INVITATION_UNAVAILABLE` error (existing behavior takes precedence).
- **VietQR Separation**: No `vietqr_photo_signed_url` is added in `M6`. The VietQR account verification remains decoupled from general wedding media storage.

## M. Guest Web Behavior
- **Consuming URL**: The Guest Web SPA extracts `cover_photo_signed_url` from the resolve DTO. If present, it renders the cover photo. If null, it defaults to the standard template layout.
- **URL Expiry UX**: Expired media URLs must not break the core RSVP flow. If an image fails to load (HTTP 403/404 on the media URL), the SPA degrades gracefully by showing a placeholder or omitting the cover block.
- **Token Privacy**: The signed media URL is never saved to `localStorage`, persistent analytics databases, or client-side telemetry trackers.

## N. Flutter Organizer UX
The Android application provides a cover image settings block in the Wedding Workspace screen:
- **States**:
  - *No Cover*: Shows a standard banner placeholder with an "Upload Cover Photo" button.
  - *Cover Available*: Shows the cover thumbnail, upload timestamp (optional), and a "Change Cover Photo" button.
  - *Uploading/Replacing*: Displays a progress indicator spinner and disables the button to prevent duplicate submissions.
  - *Archived/Read-only*: Hides the upload/replace buttons, displaying the current cover image in a static view.
  - *Error States*: Shows explicit messages for "Image type not supported", "Image too large (> 5MB)", and "Upload failed. Please check connection."
- **Stand-alone Delete Action**: Out of scope. Replacing the image is the only supported mutation.

## O. Archived Behavior
- **Organizer**: Authenticated workspace members can read the current cover image. Upload/replace mutations are blocked.
- **Guest Web**: When a wedding transitions to `ARCHIVED`, `D-INV-001` returns `404 INVITATION_UNAVAILABLE`, preventing new signed cover URLs from being generated for public guests.

## P. Security Invariants
1. **Public Direct Read Denied**: Guests cannot access `wedding_media` bucket objects directly.
2. **Caller Identity Verification**: RLS on `storage.objects` parses the wedding ID prefix in the object path and asserts that `auth.uid()` is an active member.
3. **No SVG Payload**: SVG uploads are explicitly rejected by client-side mime filters and bucket constraints.
4. **Stale/Archived Lock**: Archive status locks all write permissions in RLS.

## Q. Test Strategy
1. **Database pgTAP tests**:
   - Verify that authenticated user from Wedding A cannot insert to/select from path `weddings/wedding_B/cover.webp`.
   - Verify that authenticated Collaborator from Wedding A can insert to/select from path `weddings/wedding_A/cover.webp`.
   - Verify that anonymous users are denied SELECT/INSERT on `storage.objects`.
   - Verify that when `weddings.status = 'ARCHIVED'`, insertions/updates to `weddings/wedding_A/cover.webp` fail.
2. **Edge Function integration tests**:
   - Mock a valid cover object in storage and verify `/v1/invitation/resolve` returns a signed URL.
   - Verify that `/v1/invitation/resolve` returns `null` for `cover_photo_signed_url` if the file does not exist.
3. **Flutter widget/unit tests**:
   - Verify WebP image compression outputs file size constraints.
   - Verify error messages display correctly on upload failures.

## R. Explicit Out-of-Scope
- Archiving trigger endpoint (`api_v1.archive_wedding`).
- Deleting trigger endpoint (`POST /v1/organizer/weddings/delete` / `TOP-WED-004`).
- Storage recursive folder cleanup loop.
- Multi-photo galleries, video uploads, vendor libraries.
- Cloudflare R2 integration (post-MVP).
- VietQR dynamic image storage in `wedding_media`.

## S. M7 Dependency Note
The future `M7 — Wedding Lifecycle & Cleanup` milestone will depend on this storage foundation to list and delete all file assets located under `weddings/{wedding_id}/` prefix using the Supabase Storage Admin API inside the workspace delete handler. The precise execution architecture for `TOP-WED-004` (Edge Function vs. database-coordinated) will be evaluated and decided in the `M7` design phase.

## T. Resolved Decisions
- **`DEC-B-003`**: Resolved by establishing the static object path convention `weddings/{wedding_id}/cover.webp` inside a private `wedding_media` bucket.
- **Signed URL TTL**: Configured dynamically to **30 minutes** (1800 seconds).

## U. Implementation Conflicts
No contradictions identified. The M6 specification respects all physical database constraints and preserves the security boundaries established in the RLS and guest API review documents.
