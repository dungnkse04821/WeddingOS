4. `Side`
5. `PrimaryGroup`

7. `Party Display Name`
8. `Invited Count`

## C. Party Key Semantics

Party grouping is driven only by `Party Key`.

*   Same nonblank `Party Key` creates one intended `InvitationParty` for that import.
*   Different `Party Key` values create different parties.
*   Blank `Party Key` creates a Guest with `invitation_party_id = NULL`.
*   No grouping is inferred from surname, phone, address, PrimaryGroup, row proximity, or invited count.

Because no approved persisted Party Key identity exists for existing parties, import Party Keys are import-local. Confirm Import does not match existing parties by display name alone and does not silently attach imported Guests to unrelated parties.

## D. Local Parsing And Preview

Flutter parses `.xlsx` bytes locally using the pure-Dart `excel` package. Android file selection uses a small native `MethodChannel` wrapper around `ACTION_OPEN_DOCUMENT` and accepts the `.xlsx` MIME type.

Raw XLSX files are not uploaded, not stored in Supabase Storage, and not persisted as ImportDraft records. The import draft is local screen state only.

Preview shows:

*   row number;
*   Guest name, phone, email;
*   Side and Guest Source;
*   PrimaryGroup mapping;
*   Party Key, Party display name, and Invited Count;
*   status: `VALID`, `WARNING`, `MAPPING_REQUIRED`, or `ERROR`;
*   duplicate and creation warnings;
*   summary counts and row-status filtering.

## E. Validation And Duplicate Warnings

Client validation covers required Guest name, max name length, phone/email shape, Side values, Guest Source mapping, Party Key consistency, positive Invited Count, Party facts requiring Party Key, and Group/Party preview warnings.

Duplicate warning behavior:

*   normalized phone is a strong warning;
*   normalized email is a warning;
*   exact lowercased name match is a weak warning;
*   warnings are detected both within the imported file and against existing same-Wedding Guests;
*   warnings do not auto-merge and do not block Confirm when acknowledged;
*   duplicate warnings do not leak other Weddings.

Client never writes `normalized_phone` or `normalized_email`.

## F. PrimaryGroup Behavior

PrimaryGroup mapping is exact same-Wedding name matching. Missing groups are shown in Preview as warnings and are created once during Confirm. Multiple imported Guests reference the same created Group.

No fuzzy matching or global uniqueness assumption was added.

## G. InvitationParty And Invited Count

For every new nonblank Party Key, server Confirm creates one `InvitationParty` with consistent party-level facts:

*   `Party Display Name`;
*   positive `Invited Count`.

Rows sharing a Party Key must use the same party display name and invited count. Inconsistency is a fatal validation error and the server rejects Confirm atomically.

`Invited Count` remains independent from named Guest count. The import does not recalculate it and does not create fake Guest rows for unnamed companions.

## H. TOP-GUE-004 Server Implementation

Added `api_v1.confirm_guest_import(p_request_id uuid, p_wedding_id uuid, p_rows jsonb)` in `BATCH-06`.

The function is:

*   `SECURITY DEFINER`;
*   owned by `trusted_function_owner`;
*   executable by `authenticated`;
*   guarded by `auth.uid()` as business actor;
*   restricted to active `OWNER` / `COLLABORATOR` Wedding members;
*   denied for `ARCHIVED` / `DELETING` Weddings through the active Wedding check.

The server revalidates all rows and applies Groups, Parties, Guests, and receipt in one transaction.

## I. Request ID, Receipt, And Hash

`TOP-GUE-004` uses durable receipts in `private.trusted_operation_receipts`.

Client generates one UUID v4 `request_id` per logical confirm attempt and reuses it for retry after network failure.

Server derives SHA-256 `request_hash` from semantic material facts:

*   operation type;
*   Wedding ID;
*   ordered import rows;
*   Guest name, phone, email, Side, PrimaryGroup, Party Key, Party display name, Invited Count, Guest Source.

Excluded from the hash:

*   `request_id`;
*   UI-only status;
*   local file path;
*   raw XLSX bytes;
*   row rendering metadata.

Row order is preserved in canonicalization because the import array order is part of the submitted logical batch and supports deterministic error addressing.

Receipt stores only operation type, actor, request_id, wedding_id, request_hash, result_resource_id = wedding_id, and minimal count summary. It does not store raw XLSX, full payload, PII rows, tokens, bank data, or full response bodies.

## J. Atomicity And Retry

Confirm Import is all-or-nothing. Fatal server validation failure creates no partial Guests, Groups, Parties, or receipt.

Retry behavior:

*   same operation + actor + request_id + same semantic payload returns replayed success from durable receipt;
*   no duplicate Guests, Groups, or Parties are created;
*   same request_id with a different semantic payload raises `REQUEST_ID_REUSED`.
